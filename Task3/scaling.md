# Масштабирование баз данных

## Репликация master-slave

- Campaign: master для записи, read replica для nearline-выгрузок в кеш Bidding и для Dashboard. Выгрузки перестают конкурировать с CRUD кампаний
- Finance: master + синхронная реплика (synchronous_commit = remote_write на реплику), RPO около нуля, реплика же принимает чтение балансов для кабинета

## Шардирование

- Campaign: шардирование по `campaign_id`, а не по рекламодателю. В AdTech рекламодатели образуют длинный хвост, пара крупных аккаунтов с миллионами показов забьёт hot shard, если класть их целиком на один узел. Кампании распределяют ту же нагрузку ровно, а бюджет и ставки живут на уровне кампании, так что транзакции остаются локальными шарда
- Finance: сначала не шардируем вообще, транзакций списаний на порядки меньше, чем RTB-запросов, их держат реплика и кеш бюджета в Redis. Если окажется мало, шард по `advertiser_id`, но крупных рекламодателей дробим на субсчета (balance shard 0..N), чтобы один аккаунт не создал hotspot
- ClickHouse: партиционирование по `toYYYYMMDD(ts)`, строки раскидываем по шардам хешем `event_id`. Крупная кампания так не соберёт hot shard, а OLAP-запросам строки одной кампании на одном узле и не нужны
- Kafka: партиции по ключу `campaign_id`, порядок событий внутри кампании сохранён, потребители масштабируются партициями

Шардирование PostgreSQL включаем только при реальном росте. До 50 000 RPS RTB-трафика OLTP-нагрузка Campaign и Finance остаётся умеренной: ставки живут в кеше, события уходят в Kafka, в PostgreSQL остаётся CRUD кампаний и финансовые транзакции. Чтение прикрывают реплики, а частота записи на этом этапе не упирается в один мастер. Преждевременный шардинг бюджет не окупит.

## Read replicas для аналитики

В старом смысле не нужны: аналитика вообще уходит из PostgreSQL в ClickHouse, где реплики кластера держат и отказоустойчивость, и чтение отчётов. Для Campaign read replica закрывает выгрузки и кабинет.

## CQRS

CQRS применяется для связки Statistics → Analytics.

- Запись: события летят в Kafka и вставляются в ClickHouse батчами, write-модель оптимизирована под вставку
- Чтение: отчёты считаются в материализованные вьюхи (read-модель), кабинет читает готовые агрегаты
- Согласованность eventual: отчёт отстаёт на секунды, для рекламодателя приемлемо, для аукциона эти данные не в пути запроса

Для Finance CQRS не берём, там списания должны видеть баланс немедленно.
