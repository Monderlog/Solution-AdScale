# Database per Service

| Сервис | Тип БД | Обоснование |
|---|---|---|
| Bidding | Redis (кеш) + in-memory, своей СУБД нет | В пути запроса нет транзакций, нужны чтения за миллисекунды, а не гарантия записи. Конфиг приходит из Campaign, события уходят в Kafka |
| Campaign | PostgreSQL + read replica | Реляционные сущности с жёсткими инвариантами (статус, бюджет, валидность таргетинга), нужны транзакции и ограничения на уровне схемы, объём умеренный |
| Statistics (ingest + хранение) | Kafka → ClickHouse | Stats Ingest пишет события в Kafka, ClickHouse потребляет их оттуда. Миллиарды событий в месяц, append-only нагрузка. Колоночная ClickHouse сжимает события в разы и держит массовую вставку батчами, PostgreSQL с такой записью не справится (что видно на AS-IS) |
| Analytics | ClickHouse (реплика Statistics) | Тяжёлые агрегатные запросы должны жить отдельно от OLTP. Материализованные вьюхи считаются на вставке, отчёт в кабинете отвечает за секунды |
| Finance | PostgreSQL + синхронная реплика | Деньги, тут нужны ACID-транзакции, блокировки строк бюджета, строгие ограничения, колоночная БД не подходит |

Правила: чужую базу не читает никто, кроме владельца сервиса. Кросс-сервисные данные берутся через API или события Kafka. Схема каждой базы версионируется миграциями в репозитории сервиса.
