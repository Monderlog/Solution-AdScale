# Паттерны надёжности

## Circuit Breaker

Breaker ставим в трёх местах.

1. Gateway → Bidding: outlier detection, при открытии цепи отвечаем быстрым no-bid (см. api-gateway.md).
2. Bidding → Delivery/Campaign: вызовы обёрнуты в breaker (go-resilience). Зависимость дёргается только в nearline-режиме, поэтому открытый breaker почти не влияет на аукцион, работаем кешем.
3. Bidding → Redis: при деградации кластера переходим на in-memory копию последнего снапшота кампаний и floor-ставки.

Пороги nearline-breaker: 10% ошибок в окне 30 с или P95 вызова > 60 мс, half-open каждые 10 с, три успешных вызова закрывают цепь. У outlier detection на Gateway свои пороги, они в api-gateway.md.

## Повторы с экспоненциальной задержкой

Ретраи только для идемпотентных операций и только внутри оставшегося бюджета времени. Одна попытка, задержка 20 мс с джиттером, дальше fallback вместо ожидания. Для nearline-выгрузок из Campaign в кеш обычная схема: 1 с, 2 с, 4 с, максимум 5 попыток, с джиттером, чтобы все поды не вернулись одновременно.

## Идемпотентность финансовых операций

Идемпотентность списаний обеспечивает `event_id`, который Bidding генерирует до публикации в Kafka. Повторная доставка того же события не должна создавать второе списание.

- `event_id` служит уникальным ключом списания, в Finance он кладётся unique-индексом, повтор вставляет no-op; если сервис при сбое опубликовал победу дважды, оба дубля схлопнутся на этом индексе
- потребители идемпотентны по offset+ключу, ретрансляция топика не создаёт двойных списаний
- пополнение через платёжный шлюз идёт по external_id транзакции шлюза, тоже unique

## Резервные стратегии ставок

Аукцион должен переживать отказы, ставка собирается каскадом деградации:

1. Полная ставка из свежего кеша кампаний
2. Ставка из last-known кеша с пометкой stale, цена занижается на буфер
3. Floor-ставка по умолчанию для формата/гео запроса
4. No-bid, если даже floor не прошёл проверку бюджета

## Прочее

- Таймауты на каждый вызов из бюджета tmax, отмена по истечении дедлайна (gRPC deadline propagation)
- Bulkhead: пулы соединений к Redis и Delivery разделены, зависший Delivery не занимает пул ставок
- Load shedding: при загрузке Bidding выше 85% первыми отбрасываем запросы с низким floor, с высоким floor проходят дальше
