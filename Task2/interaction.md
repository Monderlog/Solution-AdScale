# Взаимодействие: протоколы и паттерны

## Внешний протокол: OpenRTB поверх HTTPS

С DSP говорим на OpenRTB 2.5 (JSON). Это отраслевой протокол, площадка его уже понимает, другого выбора по факту нет. JSON здесь дороже protobuf, но совместимость с партнёром важнее нескольких миллисекунд, экономим на keep-alive соединениях и HTTP/2.

## Внутренний: gRPC для Bidding ↔ Campaign/Delivery

Для путей ставок выбрали gRPC.

- Bidding и Campaign общаются постоянно и много, бинарный protobuf и HTTP/2 с мультиплексированием дают заметно меньшую сериализацию и задержку, чем JSON поверх REST. В бюджете 80 мс каждая миллисекунда на счету.
- Контракт фиксируется в .proto и версионируется, при Strangler Fig без жёсткого контракта между новым сервисом и монолитом не обойтись
- Дедлайны и отмена propagate автоматически. Если у запроса истёк tmax, отмена уходит вниз по цепочке вызовов.

REST остаётся там, где latency не критична: кабинет рекламодателя, CRUD кампаний, отчёты. Это привычный фронтенду интерфейс, и гнать его через gRPC-gateway смысла нет.

## События: Kafka, а не синхронные вызовы

Показы, клики и исходы аукционов это поток, а не запрос-ответ, поэтому события идут через Kafka. Она даёт развязку по времени: пик трафика буферизуется, БД-потребители не затапливаются. Одно событие могут независимо читать несколько подписчиков (Billing, Analytics, Stats Loader), логику рассылки дублировать не нужно. Новый потребитель может дограть историю с любого offset.

Синхронный REST для событий означал бы, что падение аналитики тормозит выдачу рекламы.

## API Gateway

Без Gateway интеграция с DSP не получается. Нужна одна точка для аутентификации, квот, circuit breaker и переключения маршрутов при миграции, а Strangler Fig без переключения трафика не работает.

Из вариантов взяли Envoy (Kong остался на случай, если захотим готовые плагины авторизации). Envoy уже стандарт для K8s Ingress, добавляет outlier detection из коробки, а плагины Kong при 18 000 RPS дали бы лишний хоп в hot path без нужды.
