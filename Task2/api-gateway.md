# API Gateway для DSP-интеграции

## Маршрутизация

- `POST /openrtb/{dspId}/bid` → Bidding Service (gRPC transcode). Новый DSP получает свой `dspId`, маршрут добавляется конфигом без релиза
- `/*` кабинета → Dashboard
- При миграции тот же роут может вести в монолит или в новый сервис, переключение весами: сначала canary 5%, потом 25%, потом 100%

## Rate limiting

Токен-бакет на `dspId`. Базовая ставка по контракту, например 4 000 RPS для новой DSP, плюс burst 10%. Сверх квоты сразу `429` с `Retry-After`, запрос до Bidding не доходит, так защищается бюджет времени всей платформы. Счётчик лежит в Redis на самом Gateway, чтобы лимит был глобальным, а не на под. Если этот Redis недоступен, каждый инстанс временно переходит на локальный бакет с долей квоты по числу инстансов, лимит грубеет, но трафик не останавливается.

## Аутентификация

Каждому DSP выдаётся API-ключ и HMAC-подпись тела запроса (`X-Signature`, timestamp ±5 мин против replay). Проверка на Gateway, Bidding получает уже аутентифицированный запрос с проставленным `X-Dsp-Id`. В кабинете обычный OAuth2/OIDC.

## Circuit breaker

Между Gateway и Bidding работает outlier detection Envoy. Он выкидывает поды с P95 выше 65 мс и долей ошибок выше 10% (у Bidding бюджет 50 мс, 15 мс запаса на внутрикластерную сеть и разброс), при открытии цепи возвращаем быстрый `no-bid`, не дожидаясь тайм-аута. Второй breaker сидит внутри Bidding на вызовы Delivery/Campaign, описан в reliability.md.

## Мониторинг времени отклика

- Гистограммы latency по этапам gateway, network, bidding, Envoy и Bidding пишут метрики с одним `X-Request-Id`
- Дашборд P50/P95/P99 на каждого DSP по пути целиком, алерт при P95 > 70 мс, за 10 мс до SLA партнёра. Порог outlier detection (65 мс) измеряет другое: время ответа Bidding глазами Gateway при бюджете сервиса 50 мс
- Данные уходят в Prometheus/Grafana, отчёты latency по каждому DSP пригодятся в разговоре о штрафах и квотах
