# TO-BE: целевая архитектура через год

Диаграмма в `diagrams/to-be.puml`.

## Выбор стиля: Strangler Fig

Оставить монолит нельзя. Hot path упирается в общую БД, критичные и некритичные потоки делят одни ресурсы, запаса по производительности нет даже под +20%.

Переписывать на микросервисы с нуля тоже нельзя. Три месяца до подключения DSP, бюджет ограничен, продукт обязан работать безостановочно, а документации, из которой можно было бы вычитать границы модулей, нет.

Берём Strangler Fig: постепенно вырезаем из монолита сервисы, пускаем трафик через API Gateway и переключаем маршруты по одному. Монолит остаётся до конца миграции, каждый шаг обратим.

## Целевые сервисы и обоснование границ

| Сервис | Граница | Почему здесь |
|---|---|---|
| Bidding Service (Go) | Приём OpenRTB-запроса, подбор кандидатов, аукцион, ответ | Самый горячий и самый чувствительный к latency компонент, выносим первым, чтобы снять нагрузку с монолита до подключения DSP |
| Ad Server | Определение пользователя, кандидаты | Пока остаётся в монолите, сильно связан с таргетинг-данными, вынесем позже |
| Campaign Service | CRUD кампаний, бюджетов, ставок | Граница по объекту «кампания», отдаёт конфиг в кеш Bidding |
| Delivery Service | HTML/JS баннера | Статичная логика, выносится дёшево |
| Stats Ingest | Приём событий показов/кликов, запись в Kafka | Убирает прямую запись событий в БД |
| Analytics | ClickHouse, отчёты | Тяжёлые запросы уходят с OLTP-базы |
| Finance Service | Списание, счета, балансы | ACID-граница, своя PostgreSQL |
| Dashboard | UI + тонкий backend | Обращается к сервисам, к базе напрямую не ходит |

## Инфраструктура

- API Gateway (Envoy/Kong) как единая точка входа DSP и кабинета, с аутентификацией, rate limiting и маршрутизацией при переключении трафика
- Kafka для событий показов, кликов, ставок и изменений кампаний
- Redis как кеш кампаний, таргетинга и бюджетов для Bidding
- PostgreSQL per service (Campaign, Finance) с репликами, ClickHouse для статистики и аналитики
- Kubernetes + CI/CD, контейнеризация, автоматический деплой, быстрый откат
- Мультирегион к концу года, два региона с приоритетно-активной схемой для SLA 99.9%

## План на год

1. Месяцы 1-3, промежуточное решение: API Gateway, Bidding Service с кешем в Redis вместо синхронной БД, Kafka для событий, выгрузка аналитики в ClickHouse. Итог: ≥18 000 RPS, P95 ≤100 мс по платформе в целом и ≤80 мс на маршруте новой DSP (там штрафы), критичный путь отделён.
2. Месяцы 4-8: Campaign Service, Finance Service, Stats Ingest, монолит теряет компоненты по одному.
3. Месяцы 9-12: Delivery, Dashboard, второй регион, SLA 99.9%, горизонтальное масштабирование до 50 000 RPS.
